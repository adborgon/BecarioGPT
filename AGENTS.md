# AGENTS.md

This file provides guidance to agents when working with code in this repository.

## Qué es este repo

BecarioGPT no contiene papers: contiene **un único script generador** (`init_paper.sh`) que crea la estructura inicial de proyectos de papers académicos (LaTeX + workflow de investigación con agentes Roo) **según el tipo de contribución**. Las plantillas ya NO están embebidas como heredocs: viven como ficheros del repo en `templates/` — `templates/common/` (SSOT compartidos por todos los tipos + `postcheck.list` común + la configuración MCP trackeada `templates/common/mcp.json` + los artefactos del motor de autonomía + los READMEs de intake de `rag/`) y un subdirectorio por tipo (`imrad`, `prisma`, `thesis`, `engineering`, `grant`), cada uno con su esqueleto `src/`, sus artefactos y su `postcheck.list`. El motor de autonomía (F4) se distribuye con el scaffold: `templates/common/` incluye `data/autonomy_state.json`, `context/autonomy_journal.md`, `context/escalation_queue.md` y el supervisor `run_autonomy.sh` (copiado a la raíz del proyecto).

## Uso

```bash
bash init_paper.sh nombre-del-proyecto                        # tipo por defecto (imrad)
bash init_paper.sh mi-revision --type prisma                  # revisión sistemática
bash init_paper.sh mi-tesis --type thesis                     # tesis/TFG/TFM
bash init_paper.sh mi-sistema --type engineering              # paper de ingeniería
bash init_paper.sh mi-ppc --type grant                        # propuesta competitiva / PPC
bash init_paper.sh nombre-del-proyecto --type prisma --force  # completar sin sobrescribir
```

- Requiere **bash real** (Git Bash/WSL en Windows): el script usa `set -euo pipefail` (línea 34) y validaciones que no funcionan en sh/dash/cmd.exe.
- `--type` es opcional: por defecto `imrad` (retrocompatible con la versión anterior). El catálogo de tipos **no está hard-codeado**: se descubre de los subdirectorios de `templates/` excluido `common/` (bloque [2]), y `usage()` lista dinámicamente los tipos detectados (bloque [3]). Un tipo desconocido (o `--type` sin valor) muestra el uso y termina con `exit 1` (bloques [4]-[5]).
- `-h/--help` muestra el uso y termina con `exit 0`. Los demás argumentos inválidos (sin proyecto, ruta que empieza por `-`, ruta con `..`, dos proyectos) muestran el uso y terminan con `exit 1` (bloque [4]). **Nunca** usa `.` como proyecto por defecto.
- `--force` solo añade lo que falta: la guarda `[ -s ]` de `write_template()` (bloque [1]) y las guardas de las copias (bloque [8]) impiden sobrescribir ficheros existentes no vacíos (protege los SSOT ya editados). Re-ejecutar sin `--force` sobre un proyecto no vacío aborta con `exit 1` (bloque [6]).
- El script copia desde **este repo** `.roomodes`, `.roo/skills/`, `.roo/rules/rules.md` (íntegro, como `.roo/rules/00_academic_core.md`; **sin heredoc de respaldo**: si falta la fuente, aborta con `[ERROR]` y `exit 1`, bloque [8.3]) y la configuración MCP trackeada `templates/common/mcp.json` (bloque [8.4], destino `.roo/mcp.json` del proyecto). No hay paso manual de copia. La copia genérica de `templates/common/` excluye `mcp.json` y `postcheck.list` (para no duplicar el fichero en la raíz del proyecto).
- No hay build/test/lint ni manifests (no existe package.json). Binarios usados: `mkdir`, `cp`, `cat`, `find`, `ls`, `printf`, `echo`, `test` (`[ ... ]`), `dirname`.
- Antes de tocar el script, verifica con la suite de humo: `bash tests/scaffold_smoke.sh` (ver sección *Gestión del repo*).

## Estructura que GENERA (es el contrato con los papers, no contenido de este repo)

Núcleo común, idéntico para todos los tipos (bloque [9]: primero se copia `templates/common/` y después el overlay del tipo elegido; los `postcheck.list` son metadatos del repo y NO se copian al proyecto):

- `.roomodes` — definición de los 5 modos académicos (copiado íntegro del repo, bloque [8.1]; el 5º, `academic-orchestrator`, es el único consumidor del bucle WP-driven).
- `.roo/rules/00_academic_core.md` — copia íntegra de `.roo/rules/rules.md` (bloque [8.3], fail-fast).
- `.roo/skills/` — las 8 skills de agentes (bloque [8.2]), incluida `s2-search` (búsqueda vía MCP).
- `.roo/mcp.json` — configuración MCP con **5 servidores** (`semantic-scholar-mcp`, `fetch` = mcp-server-fetch, `arxiv` = arxiv-mcp-server, `pubmedmcp` y `crossref` = crossref-mcp-server; bloque [8.4]): copiada sin sobrescribir destinos no vacíos desde la plantilla trackeada `templates/common/mcp.json`. **NO contiene claves API**: el servidor S2 hereda `SEMANTIC_SCHOLAR_API_KEY` del entorno del sistema y la caché de arXiv apunta a la ruta relativa `./rag/cache/papers`. Sí forma parte de la post-condición.
- `context/` — estado de investigación: `call_guidelines.md`, `hypothesis_matrix.md` (con Changelog), `evidence_notes.md` (con DOI + fecha de acceso), `autonomy_journal.md` (narrativa append-only del bucle WP-driven) y `escalation_queue.md` (decisiones D3 para el investigador).
- `data/` — `workpackages.yaml` (con un WP1 de ejemplo) y `autonomy_state.json` (espejo de estado del bucle: nace parseable con `budget` 40 iteraciones / 240 min, `current.status: PENDING` y `project_type: null` — el scaffold NO interpola; la skill `project-init` lo rellena leyendo `stats_summary.json`). `stats_summary.json` vive en el overlay de cada tipo y nace con `project_type` + `study_metadata{design, n, preregistration_url}` + `variables`; el `design` es compatible con la skill `methods-reporting` (p. ej. `systematic_review` en prisma). Todo `.json`/`.yaml` del scaffold nace parseable.
- `src/` — `main.tex` compilable, `references.bib` (única base bibliográfica, solo la edita `lit-synthesizer`) y `figures/`.
- `reviews/peer_review_log.md` — registro de auditoría académica con tabla y severidades.
- `rag/calls`, `rag/past_projects`, `rag/templates` — base de conocimiento local; `rag/cache/papers` (creada por el scaffold) es la caché de papers del servidor `arxiv`.
- `run_autonomy.sh` — supervisor fino del motor de autonomía, copiado a la raíz del proyecto (la fuente vive en `templates/common/run_autonomy.sh`; `copy_templates` la lleva al destino raíz sin exclusión, igual que los ficheros de `context/` y `data/`).
- `.gitignore` — LaTeX + Python/R.

## Post-condición y éxito

El éxito NO verifica una lista fija: el bloque [10] lee **todas las rutas** listadas en `templates/common/postcheck.list` (10 ficheros: `src/main.tex`, `.roo/rules/00_academic_core.md`, `context/hypothesis_matrix.md`, `data/stats_summary.json`, `reviews/peer_review_log.md`, `.roo/mcp.json`, `data/autonomy_state.json`, `context/autonomy_journal.md`, `context/escalation_queue.md` y `run_autonomy.sh`) y en `templates/<tipo>/postcheck.list` (4 en `imrad`, 7 en `prisma`, 9 en `thesis`, 7 en `engineering`, 12 en `grant`), y termina con `[ERROR]` y `exit 1` si falta alguna. El mensaje de éxito está en el bloque [11]: `[OK] Estructura academica generada en '<proyecto>' (tipo: <tipo>).` Los mensajes de consola son ASCII puro: `[OK]`, `[WARN]`, `[ERROR]`.

## F4 — Motor de autonomía (bucle WP-driven y supervisor)

Implementada y verificada (contrato completo en §7 del marco académico `.roo/rules/rules.md`, replicado como `00_academic_core.md`). Piezas y contrato:

- `data/autonomy_state.json` — espejo de estado (SSOT de ejecución). Nace parseable: `schema_version`, `project_type: null` (se rellena en el bootstrap de `project-init`), `budget{max_iterations: 40, timeout_minutes: 240}`, `current{wp, task, status, attempts}`, `completed[]`, `iterations_used`, `sessions[]`, `updated_at`. Estados de `current.status`: PENDING, IN_PROGRESS, BUDGET_EXHAUSTED, ESCALATED, BLOCKED, DONE.
- `context/autonomy_journal.md` — narrativa append-only (tabla Fecha/WP/Evento/Detalle/Resultado; eventos DELEGADO/VERIFICADO/FALLO/ESCALADO/CHECKPOINT/SESION_FIN). La edita el agente, NUNCA el supervisor.
- `context/escalation_queue.md` — decisiones D3 para el investigador; filas `| ESC-NNN | ... | ABIERTO |` (el supervisor las detecta por ese prefijo). Mientras haya filas ABIERTAS, el supervisor NO relanza y los WPs afectados quedan BLOCKED en el espejo.
- Modo `academic-orchestrator` (slug elegido para NO colisionar con el modo built-in `orchestrator` del host): único consumidor del bucle. Lee estado + journal + plan → elige la siguiente tarea del WP corriente → delega UN paso por `new_task` al modo responsable con criterio de aceptación explícito → verifica el criterio (`test -s`, `grep`, `latexmk`) → checkpoint (append al journal + escritura atómica del estado) → repetir. Cada delegación suma 1 a `iterations_used`. Sin grupo mcp: toda búsqueda la delega en `lit-synthesizer`. Editables solo: `data/autonomy_state.json`, `context/autonomy_journal.md`, `context/escalation_queue.md` y `rag/calls/`.
- `research-architect` con el freno redefinido en D1-D3: D1 operativa la resuelve él; D2 metodológica reversible la resuelve documentando la justificación en el journal; D3 de fondo va a `context/escalation_queue.md` (equivalente asíncrono de preguntar al investigador; en modo interactivo sigue preguntando).
- `run_autonomy.sh` — supervisor fino (bash, ASCII, `set -euo pipefail`, compatible Git Bash). Args: `--project <dir>` (default `.`), `--max-iterations N` (default 40), `--timeout-minutes M` (default 240), `--cli <comando>` (default: autodetección de `zoo`/`roo` con `command -v`), `--dry-run`, `-h/--help` (exit 0). Precondiciones: `workpackages.yaml` existe, `autonomy_state.json` parseable (con `python` o validación estructural), `escalation_queue.md` presente; si falta algo → `[ERROR]` y `exit 1`. Gate: con filas ABIERTAS o estado ESCALATED/BLOCKED imprime lo pendiente y `exit 0` sin relanzar. Sin CLI degrada a MODO MANUAL (imprime el prompt de continuación y `exit 0`). Con CLI lanza sesiones headless (prompt como primer argumento) con `timeout` de GNU coreutils si existe (si no, avisa y corre sin límite documentándolo); tras cada sesión relee el estado y decide: continuar (mientras `iterations_used < --max-iterations` y estado != ESCALATED/BLOCKED), parar por presupuesto o parar por escalación. Seguros internos: tope de sesiones = `--max-iterations` (peor caso 1 iteración/sesión) y parada si 3 sesiones consecutivas no dejan huella en el estado.
- Backoff por fuente (§7, aplicado también en `s2-search`): S2 20/40/80/160 s (máx. 4), arXiv 10/30/90 s (máx. 3), PubMed 10/30 s (máx. 3), CrossRef 5/15/45 s (máx. 3); al agotar, escalado D1 en `escalation_queue.md` + marcador `\todo{}` abierto.

Lanzar el bucle en un proyecto generado (Git Bash, dentro del proyecto):

```bash
bash run_autonomy.sh --dry-run                     # plan del supervisor sin lanzar nada
bash run_autonomy.sh                               # MODO MANUAL si no hay zoo/roo en el PATH
bash run_autonomy.sh --max-iterations 80 --timeout-minutes 300
bash run_autonomy.sh --cli roo                     # CLI headless explícita
```

## Conocimiento local RAG (intake en rag/)

Los proyectos generados incluyen 3 directorios de INTAKE (material que sube el investigador), cada uno con su `README.md` (se copian de `templates/common/rag/` con la convención de nombres `YYYY_fuente_titulo.md|pdf`; MD preferido, PDF aceptable):

- `rag/calls/` — **convocatoria vigente** (PDF/bases, criterios con pesos, formularios, notas). Lo usa `research-architect` para extraer requisitos → `context/convocatoria_checklist.md`, resumen operativo → `context/call_guidelines.md` y plazos → `data/workpackages.yaml`.
- `rag/past_projects/` — **proyectos parecidos y memorias previas del laboratorio/consorcio**: de aquí salen la estructura de laboratorio/consorcio y las pistas de estado del arte (que solo se citan tras verificarse en las 4 fuentes MCP, §6).
- `rag/templates/` — **memorias de convocatorias anteriores y guías de estilo**: de aquí sale la estructura de la convocatoria y el estilo de escritura que puntúa.

Reglas duras (§8 del marco académico): (a) todo dato de un proyecto previo se re-verifica contra el SSOT actual antes de usarse (nunca se presenta un dato viejo como actual); (b) prohibido copiar texto verbatim de memorias ajenas (estilo sí, texto no). El fileRegex de `research-architect` incluye TODO `rag/` (`^(context/.*|data/.*|rag/.*)$`); el estado del arte de grant se apoya en `rag/past_projects/` + las 4 fuentes MCP.

## Conectividad MCP (Semantic Scholar, arXiv, PubMed, CrossRef y fetch)

El scaffold copia a cada proyecto la plantilla trackeada `templates/common/mcp.json` con **5 servidores** (bloque [8.4]):

- `semantic-scholar-mcp` (`python -m uv tool run --from git+https://github.com/adborgon/semantic-scholar-mcp.git semantic-scholar-mcp serve`): buscado por `lit-synthesizer`; la clave viaja por herencia de `SEMANTIC_SCHOLAR_API_KEY` del entorno (el fichero NO contiene claves). ~1 petición/segundo.
- `arxiv` (`python -m uv tool run arxiv-mcp-server --storage-path ./rag/cache/papers`): segunda fuente de `lit-synthesizer` (preprints, CS/EE); su caché vive en `rag/cache/papers` del proyecto (creada por el scaffold). ~1 petición cada 3 s. Un preprint NO sustituye a la versión publicada.
- `pubmedmcp` (`python -m uv tool run pubmedmcp`, tras la instalación persistente única por máquina `python -m uv tool install --from git+https://github.com/dartmouth/pubmedmcp --with "mcp<2" pubmedmcp`): tercera fuente de `lit-synthesizer` (biomedicina, PRISMA) vía el API oficial de E-utilities de NCBI. El pin `--with "mcp<2"` va SOLO en la instalación: el paquete arrastra mcp 2.x, que renombró FastMCP a MCPServer y sin ese cap el servidor crashea al arrancar. La invocación de la config MCP NO lleva `--with "mcp<2"`: si un launcher concatena los args a través de `cmd.exe`, el metacaracter `<` se interpreta como redirección y rompe el arranque del server (causa raíz del bug de activación de F3-P1a); con la tool ya instalada, `uv tool run pubmedmcp` resuelve del entorno persistente en ~1 s. ~3 peticiones/segundo sin clave (hasta 10 con `NCBI_API_KEY` en el entorno; la clave JAMÁS se escribe en ficheros trackeados).
- `crossref` (`python -m uv tool run crossref-mcp-server`, tras la instalación persistente única por máquina `python -m uv tool install crossref-mcp-server --with "mcp<2"`): cuarta fuente de `lit-synthesizer` (verificación independiente de DOI/metadata y export BibTeX/RIS) vía el API oficial api.crossref.org. El cap `--with "mcp<2"` va SOLO en la instalación, mismo patrón que pubmedmcp: sin él el paquete arrastra mcp 2.x (renombró FastMCP a MCPServer) y el servidor crashea al arrancar; la invocación de la config NO lleva metacaracteres. Sin claves: la variable opcional `CROSSREF_MAILTO` (polite pool) se hereda del entorno del sistema y JAMÁS se escribe en ficheros trackeados. Uso educado del API (evitar ráfagas que provoquen 402/429).
- `fetch` (`python -m uv tool run mcp-server-fetch`): convocatorias y documentación; es el único servidor de `research-architect` (la búsqueda de literatura le está PROHIBIDA y la delega a `lit-synthesizer`).

Fuentes descartadas: **Google Scholar** (ecosistema `google-scholar-mcp`): sin licencia clara, transporte HTTP y scraping de Google con alto riesgo de CAPTCHA/ban en uso autónomo prolongado → no viable, NO integrado. **PubMed-MCP-Server (JackKuo666)**: usa el API E-utilities, pero su empaquetado no tiene punto de entrada ni build-system, arrastra el backport `asyncio` de PyPI, sus metadatos carecen de DOI y hace N+1 peticiones sin batching → se mantiene dartmouth/pubmedmcp. **crossref-MCP-Server (JackKuo666)**: candidato inicial de CrossRef, NO integrable: sin pyproject/setup.py (la instalación git+ falla), sin LICENSE, abandonado (3 commits; último push 2025-04-05), `mcp>=0.1.0` sin cap (crashea con mcp 2.x) y con un `sci_hub_server.py` roto que contamina la procedencia académica → se usa el paquete PyPI `crossref-mcp-server` 1.0.0 (SMABoundless, MIT). **OpenAlex**: descartada por decisión del usuario; no está integrada ni se planifica su integración.

`lit-synthesizer` es el único modo que busca artículos (skill `s2-search`, fases S0-S6). `academic-writer` y `reviewer-2` no tienen grupo MCP: delegan las solicitudes a `lit-synthesizer` vía `new_task`. Cada artículo se registra antes de devolver claves: evidencia (DOI/URL + fecha de acceso) en `context/evidence_notes.md` y entrada BibTeX verificada en `src/references.bib`. La sección §6 del marco académico (`.roo/rules/rules.md`, replicada como `00_academic_core.md`) regula este flujo.

Seguridad (separación config local / tracked): **la plantilla trackeada `templates/common/mcp.json` no contiene ninguna clave API** y es lo que el scaffold copia a los proyectos y lo que escanea la suite de humo. El fichero `.roo/mcp.json` de ESTE repo es configuración **local**: está en `.gitignore`, puede contener la clave del usuario y **NUNCA se commitea** (si estuviera trackeado de una versión anterior, des-trackearlo con `git rm --cached .roo/mcp.json`). No publicar este repo (ni los proyectos generados) en repositorios públicos.

## Gestión del repo

- Suite de humo: `bash tests/scaffold_smoke.sh`. Cubre, por cada tipo de `PROJECT_TYPES` (cabecera del test): generación en directorio temporal y post-condición parametrizada, parseabilidad JSON/YAML (con `python` si está disponible; validación estructural mínima si no), noclobber (re-ejecutar sin `--force` aborta; con `--force` no sobrescribe, comparación byte a byte), `-h/--help` con exit 0 y argumentos inválidos con exit 1 (incluido `--type` desconocido o sin valor), salida ASCII pura, seguridad MCP sobre la fuente trackeada `templates/common/mcp.json` y sobre el mcp.json generado en cada proyecto (sin claves `s2k-`, sin `SEMANTIC_SCHOLAR_API_KEY`, sin ruta absoluta de intérprete, sin `--refresh-package`, con las entradas de los 5 servidores (semantic-scholar-mcp, fetch, arxiv, pubmedmcp y crossref); el `.roo/mcp.json` local de este repo NO se escanea), consistencia LaTeX (`\input`/`\include` resolubles) y retrocompatibilidad (generar sin `--type` produce exactamente lo mismo que `--type imrad`). F4 añade: presencia de los 4 ficheros de autonomía y `bash -n` de `run_autonomy.sh` en cada tipo, parseabilidad de `data/autonomy_state.json` (estructura validada con `python` o chequeo estructural), snapshot noclobber con `autonomy_state.json` y `run_autonomy.sh`, y el supervisor en seco sobre un proyecto generado: `--help` con exit 0, dry-run sin CLI → MODO MANUAL con prompt y exit 0, y con una escalación ABIERTA simulada se niega a relanzar (exit 0 imprimiendo la cola). F5 añade: parseabilidad de `data/consortium.yaml` y `data/budget.yaml` cuando el tipo las define (solo `grant`).
- Añadir un tipo nuevo: crear `templates/<tipo>/` con su esqueleto `src/`, sus artefactos y su `postcheck.list` → el script lo autodescubrirá (bloque [2]) y lo listará en `usage()`.
