- `init_paper.sh` (389 líneas) es el único código del repo. Edítalo con bash estricto: `set -euo pipefail` en la línea 34. En Windows, lanzar con Git Bash/WSL.
- Las plantillas NO están embebidas como heredocs: viven como ficheros del repo en `templates/` (`common/` + un subdirectorio por tipo: `imrad`, `prisma`, `thesis`, `engineering`, cada uno con su `postcheck.list`). El catálogo de tipos se autodescubre de los subdirectorios de `templates/` excluido `common/` (bloque [2]) y `usage()` lo lista dinámicamente (bloque [3]). NO reintroduzcas heredocs de plantillas.
- Estructura del script (bloques [1]-[11]): mensajería ASCII `[OK]/[WARN]/[ERROR]` con `printf` (líneas 39-41), `copy_tree_noclobber()` (líneas 45-57), `write_template()` con guarda `[ -s ]` (líneas 62-70), `copy_templates()` (líneas 78-90; excluye `postcheck.list` y `mcp.json`), parseo/validación de argumentos y de `--type` (bloques [4]-[5]), `mkdir -p` con 10 rutas citadas (bloque [7], líneas 266-276, incluida `rag/cache/papers`), copias del marco académico [8.1]-[8.4], plantillas common+overlay (bloque [9], líneas 350-352), post-condición parametrizada (bloque [10]) y éxito (bloque [11]).
- Parseo de argumentos (bloque [4], líneas 168-207): acepta `--force`, `--type <tipo>` y `-h/--help` (el help termina con `exit 0`); rechaza rutas que empiezan por `-`, que contienen `..`, un segundo proyecto o un `--type` desconocido (usage + `exit 1`); **nunca** usa `.` como proyecto por defecto.
- Copias íntegras desde el repo con guardas de no-sobrescritura `[ -s ]`: `.roomodes` (bloque [8.1]), `.roo/skills/` vía `cp -r` o `copy_tree_noclobber` si `--force` (bloque [8.2]), `.roo/rules/rules.md` → `.roo/rules/00_academic_core.md` (bloque [8.3]; **sin heredoc de respaldo**: si falta la fuente, aborta con `[ERROR]` y `exit 1`) y la plantilla trackeada `templates/common/mcp.json` → `.roo/mcp.json` del proyecto (bloque [8.4]; copia no-clobber + `[WARN]` recordando definir la clave en el entorno). La copia genérica de `templates/common/` excluye `mcp.json` y `postcheck.list`.
- `data/stats_summary.json` vive en el overlay de cada tipo (`templates/<tipo>/data/`) y nace con esqueleto **válido y parseable** (`project_type` + `study_metadata{design, n, preregistration_url}` + `variables`); `data/workpackages.yaml` (en `templates/common/`) nace con un WP1 de ejemplo. Todo nuevo `.json`/`.yaml` del scaffold debe nacer parseable.
- El esqueleto `src/` de cada tipo vive en `templates/<tipo>/src/`: la numeración `01_introduction.tex`… codifica el orden de secciones que `src/main.tex` incluye con `\input`. Al añadir una sección, usa el número siguiente y actualiza el `postcheck.list` del tipo; no reordenes las existentes.
